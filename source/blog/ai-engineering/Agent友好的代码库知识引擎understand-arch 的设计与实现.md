## 一个前提:可靠不靠模型聪明,靠知识资产兜底

让一个 Agent 可靠地干完一件长活,模型聪明只是必要条件。一个真实的工程任务是几十步、要交接、有人参与、还得跨半年存活的连续动作,需要了解足够多的现状知识，而准确且新鲜的知识资产库是保证harness不翻车的前提。

understand-arch 是一个面向代码库架构知识资产的 Claude Code 插件。一件事,接手一个你不熟的代码库,把它编译成 Agent 可读、人可审的知识与约束体系,并随代码持续生长。

下面分四层讲:靠哪五条原则保证质量、知识编译成什么形状、怎么让它不过时、五个阶段怎么把它跑出来。

## 核心方法:五条设计原则

这五条是所有能力共用的工程姿势,不随阶段变。每一条都对准 AI 会犯的一类错。

**原则一,不重新发明已经做好的层。** 扫描代码是成熟工业品,直接复用业界高星的 Understand-Anything(31k star)当底座,自己只在上面叠治理层,把工程预算压到最值钱的那层。

**原则二,确定性和推断严格分层。** 有唯一答案的事交脚本(扫文件、算指纹、校验 JSON),需要语义判断的事交子 agent。这条边界焊死,模型推断绝不允许塞进脚本。混在一起,脚本调不了模型,语义层会整个断电。

**原则三,主上下文洁净,跨界只走结构化结果。** 子 agent 和主上下文之间,只传被 schema 锁死的结构化结果,主上下文永不直读原始代码。否则多个 Agent 各读各的、到主上下文里互相印证,出来的不是协作,是几个模型一起编故事。

**原则四,双层验收,证据强制。** 确定性脚本验一层,独立的资深 Agent 再验一层,验收的不能是干活的那个。每条推断强制回链到具体代码位置,格式不过 schema 就禁止写盘。

**原则五,人确认的权威性，决策记录只追加。** 人点过头的条目永不被 Agent 覆盖,决策、评审、状态历史都只追加,指纹驱动漂移检测。

后四条分别堵 AI 的四类错:在不该出手的地方出手、污染上下文、自说自话假装完成、把历史改没了。原则一是元原则,决定你有没有余力把后四条做扎实。

## 编译成什么:一个真相源,两种投影

知识库有个绕不开的矛盾。把代码直接编译成一份文档,人和 Agent 就得读同一份。但 Agent 要的是高密度、可定位的结构化信号,人要的是连贯易读的叙事。一份产物服务两端,必然顾此失彼。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/S8CROAYnibpGxCwOpicCAA9o3Dy7wmUgxAdBDF7H9VRD5uzafXx0dcA5Mc0h8d14icm0QlGWzNuxFg9TKY6n7vuYdSONd2ebRYjpliagfYneoicA/640?wx_fmt=png&from=appmsg&watermark=1&tp=webp&wxfrom=5&wx_lazy=1#imgIndex=2)

understand-arch 的答案是 **一个真相源、两种投影** 。底层是结构化的事实层 `specs/`,所有判断都源于它,往上派生出两种形态,各服务一端。

```nix
specs/  结构化事实 + 架构推断(唯一真相源)
  ├─ 派生 → cards/  给 Agent:高密度、可定位、一跳命中
  └─ 投影 → wiki/   给人:连贯叙事 + 架构图
```

**给 Agent 的投影是知识卡。** `cards/` 下一组高密度卡片,每张只装一个对象:焦点摘要、代码锚点、相关卡 id、源哈希。它不是新写的,是从 specs 确定性派生的。分 12 类,8 类讲架构(组件、能力、接口、风险、约束、决策……),4 类讲技术事实(API 契约、库表、外部集成、项目上下文)。工程师改一个 API,Agent 一跳命中对应卡片,不必在大库里盲目检索。

**给人的投影是白皮书和架构图。** 一篇可通读的 `ARCHITECTURE.md`,加 `/arch-diagram` 出的 SVG 图。两者都是 specs 的只读投影,图里捏造一个不存在的组件都过不了校验。

这条分层的关键是方向。 **白皮书和架构图永远是结果,不是源头。** 谁想改架构认知,改的是底层 specs,投影下次自动跟上。这就从根上避免了「文档和模型各说各话」。而源哈希一变,就知道哪张卡过期了,这又成了后面自迭代的抓手。

## 资产到底长什么样:.understand-arch 全量资产模型

所有产物只落在项目根目录下一个 `.understand-arch/{project}/` 目录,多仓共用一个,其它位置一行不碰。

```nix
.understand-arch/{project}/
├── specs/            唯一真相源:代码图谱 + 架构层 + 指纹
├── cards/            Agent 检索层:12 类知识卡(从 specs 派生)
├── wiki/             人读投影层:架构白皮书 + 架构图
├── rules/            规格约束层:规范层(人写)+ 约束层(AI 起草人确认)
├── decisions/        决策台账(ADR,只追加)
├── change-requests/  方案文档(每个变更一份)
├── improvements/     架构改进候选
├── agent-context/    给 Agent 的 AGENTS.md(用户自决软链到根)
└── state.yaml        工作流状态(单写手)
```

这堆资产按「谁读、谁写、可不可信」分四带,定位各不相同。

| 资产 | 谁读 | 谁写 | 可信度 |
| --- | --- | --- | --- |
| `specs/` 图谱 + 架构层 | Agent | 脚本 + 子 agent | 图谱是事实,架构层是待确认推断 |
| `cards/` 知识卡 | Agent | 确定性派生 | specs 的高密度投影 |
| `wiki/` 白皮书 + 图 | 人 | 渲染脚本 | 只读投影,不是真相源 |
| `rules/` 规格约束 | Agent + 人 | AI 起草、人确认 | 已确认即硬约束 |
| `decisions/` + `CR` | 人 + Agent | 人主导 | 只追加,带评审 |

specs 是地基,cards 和 wiki 是它面向两端的投影。但这套工具真正值钱的,是 `rules/` 里那批 **能拦住合并的硬约束** ——「这里不能动、为什么不能动、动了怎么报警」。

图谱开源扫描器能给,白皮书换个工具能渲。只有这批约束是独有沉淀。

`rules/` 分两层。 **规范层** 是人写给系统的规矩,永久权威,Agent 只读。 **约束层** 是系统反过来告诉人的护栏,Agent 起草、人确认才作数。

每条约束 7 个字段落地:约束内容、代码依据、证据等级、检测命令、状态、来源、备注。前一篇那五条产权规则,全焊在这 7 个字段里。

**产权就刻在「状态」和「来源」两个字段上。** schema 卡死一条规则:来源是 AI 挖的,状态就不准是「已确认」。只有人改了来源、填了确认人,才能升级。校验不过,直接拒绝写盘。

## 让知识活着:双飞轮自迭代

知识库最大的敌人是过时。人为什么放弃维护文档?不是不会写,是维护的记账成本涨得比知识价值还快。但脚本不会累,它的维护成本趋近于零。

understand-arch 用两个相互独立、又相互喂养的飞轮,让知识库随开发活动自动生长,不需要人专门维护。

**代码侧飞轮** 由 commit 触发。每次提交按 diff 增量更新受影响的卡片和图谱,白皮书跟着刷新——写代码就是在喂知识库。

**决策侧飞轮** 由合入的方案和决策触发。一个子 agent 从合入的 CR 和 ADR 里,把当初拍板的约束抽回约束层。另一个从 git 历史里挖信号,共同变更、热点,转成候选约束和反常点。

两个飞轮一边追代码现状,一边沉淀决策意图,都自动跑。但有一条铁线:**自迭代喂进来的全是「待确认」,飞轮再快也越不过产权线** 。模型只负责把变化翻译成候选,确权永远归人。

飞轮的传感器是指纹漂移检测。引擎给每个文件、函数、类算内容指纹,下次扫描比对新旧、判新鲜度:没变就用缓存;代码变了但架构没动,标记存疑等审计;架构节点真动了,直接拦住后续设计,提示先刷新基线。

## 完整能力栈:五阶段工作流

把上面的方法落到系统里,是一条从代码到可演进资产的流水。五个阶段有时序、有交接,但每个阶段都跑同一套骨架:**确定性脚本打底,子 agent 做推断,独立 agent 验收** 。整套工具一共 23 个子 agent,严格按这套骨架编排,生产的和验收的从不是同一个。

| 阶段 | 入口 | 把什么变成什么 | 主产资产 |
| --- | --- | --- | --- |
| 一 扫描建图 | `/arch-onboard` | 代码 → 知识图谱(事实) | `specs/` 图谱 |
| 二 推断挖掘 | 架构师层编排 | 图谱 → 架构层 + 知识卡(待确认) | `arch-layer` + `cards/` |
| 三 访谈确认 | `/arch-interview` | 老员工脑内的「为什么」→ 留底约束 | `constraints/` 人证 |
| 四 治理沉淀 | `/arch-design` | 待确认 → 已确认 | 硬约束 + 方案文档 |
| 五 演进审计 | `/arch-audit` | 静态资产 → 自迭代的活资产 | 漂移报告 + 决策回流 |

## 阶段一 · 扫描建图

接手一个七十万行的老项目,第一件事是搞清楚里面有什么。没有可信的图谱,后面全是空中楼阁。

这层我没自己写。Understand-Anything 把「代码 → 知识图谱」做成了一条成熟流水,跨多语言、跨增量、跨子域去重,整仓 fork、一行不重写。每个仓库各扫一遍产出独立图谱,节点 id 加仓库前缀支持多仓,再用脚本做跨仓连边。这些动作有唯一答案,纯脚本干,模型插手只会更慢更飘。

我重点加深的是底座的 parser。工程师改一个 API 或一张表,要的不是「这里有个 endpoint」这种粗节点,而是参数、响应、字段、索引、外键、外部配置 key 这些技术细节。所以 graphql、openapi、sql 几个 parser 都被强化,把细节全挖进 graph 节点。 **关键是这些事实只进 graph 这一处,不另建并列 JSON** ——改一个 API 只更新一处,cards 自动派生、wiki 自动重渲。

## 阶段二 · 推断挖掘

图谱告诉你「代码里有什么」,但架构师真正要的是「为什么这么写」和「哪里埋着雷」。这两样图谱里没有,得在图谱之上长出来。这是这套工具的核心竞争力,也是信息密度最高的一阶段。

编排把推断切成几个互不干扰的环节,每个派一个专职子 agent。每个 agent 在自己的上下文窗口里读代码,只把 schema 锁定的结果交回主上下文。主上下文不碰原始代码。每条推断强制带证据,证据不足就记进「已知的未知」,不许编。

最核心的一个 agent 是 `arch-constraint-miner`,一趟产三份同源产物:

- **隐性约束考古**,从代码行为反推依赖方向、数据不变量、接口承诺。
- **反常点地雷地图**,7 类反常带可疑度评分,作下一阶段访谈的题库。
- **编码事实约定**,多数派统计,95% 命中算强约定。

三份全部默认「AI 挖掘 + 待确认」。 **这一阶段不允许 AI 产任何「已确认」。**

## 阶段三 · 访谈确认

有一类信息机器考古拿不到。「issued 后金额为什么不可变」,机器扫得出「是什么」,扫不出「为什么」,那条规则背后可能是一次审计事故,只活在老员工脑子里——而且大多数时候他自己都意识不到自己知道。

抢救「为什么」是工程问题,不是组织问题。别开「上下文审计会」,问「这模块有什么坑」,老员工想半天什么也想不起来。 `/arch-interview` 把自己当成一个严谨的新员工,拿上一阶段的反常点清单当题库、按可疑度排序,一次只问一个,每问附一个 AI 推荐答案,老员工只做选择题。

```
我发现 src/billing.py:142 有一段 try-except: pass,异常被吞掉。
我的猜测:为了应付偶发的网络超时。
请确认:这是有意为之吗?背后的原因/约束是什么?
```

产出统一标「访谈」来源,权重高于 AI 挖掘,但仍是待确认。 **把人的判断力用在拍板上,把人的体力省下来——这是抢救隐性知识唯一跑得动的工艺。**

## 阶段四 · 治理沉淀

前三阶段产的全是待确认。这一阶段把够格的升为已确认,沉淀成项目能长期依赖的硬约束。核心问题只有一个:**怎么让 AI 没办法绕过人的终审、也没办法假装完成。**

产权 schema 拦着 AI 自标已确认,双层验收换人站岗,约束消费带拦截。

最值得说的是方案设计本身,被做成了一道 **分级闸**:

1. 先盘问 PRD,挑出含糊目标和卡住设计的未知。未知太多,直接停下来问人。
2. 过关才出 3 个候选方案,给人选。
3. 人选定后,再深化接口和模块边界。
4. 最后才落成正式方案。

**「先逼问清楚、再给选项、最后才动笔」,拦的就是 AI 最爱干的事:拿着含糊需求,直接产一份看起来很完整的方案。**

## 阶段五 · 演进审计

工程资产不是写完就完。代码会变、需求会变、理解会深,一套不能演进的资产,半年就成考古文物。这一阶段靠双飞轮自迭代加指纹漂移检测(前面已展开),让资产像 git 一样有版本、可比对。

这里的两个挖掘 agent——一个从合入的方案和决策抽约束,一个从 git 历史挖信号——都只能产「待确认」,跟阶段二一个规矩。自迭代喂进来的东西照样要过人确认那道关。主力仍是确定性脚本,算指纹、判新鲜度都有唯一答案。 **模型在这一章只负责把信号翻译成候选,确权永远不归它,这恰恰是它可靠的原因。**

## 工程化落地:让它真的能用

前面五个阶段是分开讲的,但真跑起来,它们是一个 **闭环** 。一条知识从诞生到老去,在这个环里走完整圈。

一条知识的生命周期是这样的:**扫描** 时作为代码事实诞生,**推断** 时被 AI 起草成待确认候选,**访谈** 时补上代码看不见的「为什么」,**治理** 时由人确认升成硬约束。升级之后它不是终点,而是进入循环:代码一改,**演进审计** 用指纹发现它可能过期;双飞轮从新提交和新决策里又挖出新候选,回流成「待确认」,重新走一遍确权。

**整个环只有一个口子放行——人确认那道关。** 不管知识从机器考古来、从访谈来、还是从自迭代回流来,要变成能拦合并的硬约束,都得过这一关。这是整套设计的产权底线。

下面给一份在自己项目落地的实操路径。

**第一步,建基线。** 在项目根目录跑 `/arch-onboard`,多仓项目它会自动发现兄弟仓库并问你纳不纳入。跑完你会拿到知识图谱、架构白皮书、一批待确认约束,以及一份「它没搞懂的清单」(known\_unknowns)。第一次别指望全自动,重点看 known\_unknowns 和反常点清单。

**第二步,抢救隐性知识。** 趁还找得到人,拉上项目里的资深同事跑一轮 `/arch-interview` 。它会拿反常点清单按可疑度排序、一题一题问,每题带 AI 推荐答案,对方只需确认或纠正。这一步产出的是代码里永远挖不出来的「为什么」,是这套工具最值的一段时间投入。

**第三步,确权。** review 一遍待确认约束,把你认可的升成已确认,给每条挂上能跑的检测命令。 **这一步是人的核心工作,也是唯一不能外包给 AI 的一步。** 确认得越多,后面方案设计时的护栏越密。

**第四步,接进日常。** 跑一次 `/arch-onboard --enable-hooks` 打开钩子,之后每次 git 提交自动触发增量刷新,知识库跟着代码走。日常设计新功能走 `/arch-design`,它会自动拿已确认约束当护栏拦你;想知道基线还可不可信就跑 `/arch-audit`;想找重构机会用 `/arch-improve` 。

维护上记住三条就够了。

**一,别追求一次确认完**,约束层是慢慢长厚的,每次 design 碰到相关待确认约束时顺手确认即可。

**二,定期跑 audit**,尤其大重构后,看漂移报告决定要不要重建基线。

**三,把 `.understand-arch/` 一起提交进 git**,它本来就是设计成跟代码同仓演进的,团队共享、历史可追都靠这个。

最后是几条让它在真实团队里站得住的工程边界。

**产物不污染仓库。** 全部产物只落在一个 `.understand-arch/` 目录。连给 Agent 用的 `AGENTS.md` 也产在这里,要不要软链到仓库根用户自决,工具绝不擅自往根目录写、改任何文件。

**加深而不加层。** 补技术深度时最容易犯的错,是新建一个并列的技术参考 JSON、再建一个并列的文档目录。我没这么做:技术事实只进 graph,cards 扩出技术卡,wiki 对应章节加段投影。 **判断设计有没有冗余有个朴素标准:改一个 API 要同步几处?答案必须是一处。**

**接得住中断。** 工作流状态记在单写手的文件里,内部 skill 只上报增量。长任务跑到一半崩了能续,不必从头来。

工具已经开源,完整实现在 [https://github.com/ttttstc/understand-arch,欢迎去翻代码、提](https://github.com/ttttstc/understand-arch,%E6%AC%A2%E8%BF%8E%E5%8E%BB%E7%BF%BB%E4%BB%A3%E7%A0%81%E3%80%81%E6%8F%90) issue,或者直接拿去改成你自己团队的那一套。
