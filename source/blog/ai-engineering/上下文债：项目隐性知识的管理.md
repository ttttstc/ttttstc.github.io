## 一、先说清楚一个概念：上下文债

软件行业过去几十年说"技术债"，默认指的是代码债，比如写得脏的代码、欠的测试、没做的重构。这种债是看得见的，可以拿 SonarQube 扫出来，可以做 burn-down chart。

但还有另一种债是看不见的，从来没被严肃讨论过。

那就是上下文债。

什么叫上下文债？就是"那些只存在于人脑里、没被显式写下来、不能被 review、不能被版本化、不能被传承"的项目知识。一个团队的上下文债越重，越依赖那几个老员工的"在场"。老员工一旦离职，债务直接违约。

代码债和上下文债有个根本区别。

代码债是线性增长的，写多少烂代码就有多少债。

上下文债是指数增长的，因为它会传染。一个团队上下文债重，老员工就要花更多时间口头解释，少写代码、少写文档，导致更多上下文债。新员工接手时间长，老员工耐心耗尽，文档写得更敷衍，债越滚越大。

AI 时代之前，上下文债的危害被"勤奋的老员工"对冲掉了。AI 时代之后，这个对冲失效了。因为 AI 没法读老员工的脑子。

这件事的根本变化是：上下文债从"隐性问题"变成了"显性瓶颈"。它直接决定了 AI 工具在你团队能发挥几成功力。

如果你的团队上下文债很轻，AI 工具能发挥 90% 的功力。它读得懂规则、读得懂意图、读得懂边界。

如果你的团队上下文债很重，AI 工具最多发挥 30%。它在猜，在赌，在自由发挥。然后你的新同事跟着它的判断，删掉了一个不该删的运维资源。

我开始系统性地观察这件事在行业里是怎么被讨论的，越看越觉得，我们团队遇到的不是个案，是一个所有维护过老代码的团队都在反复遭遇的问题。而最近一年多，整个行业其实正在围绕这个问题做一件事：把"上下文"本身工程化。

## 二、一个被低估的信号：AGENTS.md 已经成了开放标准

如果你最近 clone 过一些活跃的开源项目，可能注意到根目录里多了一个文件叫AGENTS.md。它看起来跟 README 没什么两样，所以大部分人会忽略它。

2025 年 7 月，Sourcegraph 的 Amp 团队发起了 AGENTS.md 这个格式。8 月，Google、OpenAI、Factory、Sourcegraph、Cursor 联手把它推成开放标准。同年 11 月，Linux Foundation 旗下的 Agentic AI Foundation 正式接管这个标准。

AGENTS.md 的逻辑本身不复杂，就是一个 markdown 文件，写清楚这个项目怎么 build、怎么测试、有什么约定、有什么坑。但是它的意义不在文件本身，而在于一件更深的事 ——整个行业第一次承认，"给 AI 看的项目说明"是一个独立的、值得标准化的工程产物。

这跟 README 是两件事。README 是给人看的，AGENTS.md 是给 AI 看的，但 AI 读完之后还要把读懂的东西执行出来。所以它必须更结构化、更精确、更"机器可读"。

理解这件事的分量需要换一个角度。在过去，"项目知识"这种东西的载体是什么？是 wiki，是 Confluence，是某个老员工的脑子。它们的共同特征是不可执行。AGENTS.md 是历史上第一种"可执行的项目知识载体"。

## 三、Anthropic 和 OpenAI 在两件事上的具体做法

Anthropic 的 Claude Code 和 OpenAI 的 Codex 是这个领域走在最前面的两个工具。它们在两个地方的设计值得重点对照：一是怎么管理"工程现状的上下文"，二是怎么处理 handoff（任务交接和新人接入）。前者决定了 AI 能不能跟得上代码演化，后者决定了知识能不能从一个人传到下一个人。这两件事是判断一个 AI 编程工具能否真正用于大型遗留工程的核心指标。

先看上下文维护。

Anthropic 用的是"分层式"。最底下是CLAUDE.md，存项目级的持久化记忆，每次 session 启动自动加载。再上面是 Skills，按需触发的专业知识包，只在相关任务出现时才加载到上下文里。最上面是 Hooks，13 个生命周期事件，每次必然执行的强制规则。

OpenAI 用的是"指令链式"。从~/.codex/AGENTS.md（全局）到/AGENTS.md（项目根）到子目录AGENTS.override.md，越靠近当前文件的指令优先级越高。这跟 Linux 的多级 config 或者 Git 的层级配置同构。

两家最关键的差异是这一条 ——

> CLAUDE.md / AGENTS.md 里写的东西， **本质都是 advisory（建议性）的** ，AI 不一定每次都遵守。

Anthropic 的解法是 Hooks 系统。把 advisory 和 deterministic（强制性）分开。"这个项目用 TypeScript 严格模式"写在 CLAUDE.md 里，是建议；"任何 commit 之前必须跑 lint 并通过"写成 PreToolUse hook，是强制。Hook 在底层每次必然触发，AI 没法绕过。

OpenAI 没有等价的 hook 系统，它把强制性交给了 CI/CD 流水线和 Codex 自己的内部评审机制。OpenAI 公开过一个数字 —— Codex 评审了内部 100% 的 PR。

这个二分非常重要。很多团队把 AGENTS.md 当万能药，结果发现 AI 还是会偶尔不守规矩。不是 AI 不听话，是因为这些规矩本来就在"建议性"层级。真正不能违反的事情，必须写成 Hook 或 CI 强制 check，不能只写在 markdown 里。

再看 handoff 这件事。

OpenAI 的方案显式且工程化。Codex Agent SDK 里有一套显式的多 agent handoff 模式：Project Manager 写REQUIREMENTS.md和AGENT\_TASKS.md，然后 handoff 给 Designer、Frontend、Backend、Tester。每个 agent 写出自己范围内的 markdown deliverable，整个交接过程被自动 trace 记录下来。

这是一个很有启发的设计 ——每次 handoff，都产出一份显式的、可审查的、可追溯的文档资产。这跟传统的"开个会同步一下"完全不是一个量级。

Anthropic 的方案更轻量。用 Subagents 实现"上下文隔离的有界委托"：主 agent 把一个明确范围的子任务委托出去，子 agent 在隔离的上下文里完成，只把最终结果传回。配合 Skills，可以做到"每个领域的专业知识在需要时才加载、用完就释放"。

这两种 handoff 模式对应两种典型场景。OpenAI 的方案适合有明确分工的大型任务，Anthropic 的方案适合单人主导但需要专业知识切换的迭代式开发。

| 对比维度 | Anthropic (Claude Code) | OpenAI (Codex) |
| --- | --- | --- |
| 上下文载体 | CLAUDE.md（项目级）+ Skills（领域级） | AGENTS.md（多级指令链 + override） |
| **强制规则机制** | **Hooks 系统** （13 个生命周期事件，必然触发） | **依赖 CI/CD 流水线 + 内部 PR 评审** |
| Handoff 模式 | Subagents（轻量隔离委托） | Agent SDK 显式多 agent 流水线 |
| Handoff 产物 | 子任务结果回传 | 每阶段 markdown deliverable + trace |
| 适合场景 | 单人主导的迭代式开发 | 多角色分工的大型项目 |

## 四、显式 markdown 还是向量索引？答案是双轨

国内大厂走的是完全不同的另一条路线。

阿里通义灵码和腾讯 CodeBuddy 不靠 AGENTS.md，它们靠向量索引。打开项目，IDE 后台自动把整个 codebase 切分、向量化、建立索引。之后你问任何问题，系统先做语义检索，把相关代码片段塞进上下文。

腾讯公开过 CodeBuddy 的 Codebase 实现细节。用 embedding 模型把代码文件切分为函数、类等逻辑单元生成高维向量，分层索引策略对 src/ 这种高频修改目录做实时更新，对 node\_modules 等静态依赖做惰性加载。阿里通义灵码也类似，打开项目时自动向量化，索引以增量方式进行，新建或修改的文件实时处理，无需人工干预。

两条路线的对比可以这样看：

| 维度 | 路线 A：显式 Markdown | 路线 B：向量索引 |
| --- | --- | --- |
| 代表 | Anthropic、OpenAI、Sourcegraph | 阿里通义灵码、腾讯 CodeBuddy、Cursor 部分功能 |
| 知识载体 | AGENTS.md / SKILL.md | 向量数据库 + RAG |
| 维护方式 | 人工写 + Git 版本化 | 自动增量索引 |
| **是否可 Review** | **是** （PR、diff、code owner） | **否** （向量黑盒） |
| **跨工具兼容** | **强** （开放标准） | **弱** （厂商绑定） |
| **自动同步代码变更** | **弱** （需要人工同步） | **强** （自动） |
| 适合承载的内容 | 设计意图、规范、约定、流程 | 代码间语义关联、跨文件依赖 |
| 主要失效模式 | Spec drift（规约漂移） | 黑盒，无法 debug |

讨论这两条路线哪个更好，其实是个伪问题。它们承载的根本不是同一类信息。

显式 markdown 承载的是"显性知识"，包括团队约定、设计原则、不能违反的规则。这些东西必须可被 review、可被 PR、可被传承。

向量索引承载的是"隐性知识"，包括代码之间复杂的语义关联、跨文件依赖、相似实现的发现。这些东西人工写不出来，必须靠机器扫描。

成熟的工程团队应该是双轨制。显式那一轨保证团队规则的传承性和可审计性，向量那一轨保证 AI 对代码本身的深度理解。只搞一边都是半桶水。

我们团队那个故障如果只靠向量索引，新同事还是会出错。因为"为什么不能删"这种意图层面的信息，根本不在代码里，向量化也无能为力。这种东西只能靠显式 markdown 承载。

反过来，如果只靠 AGENTS.md，但项目有 70 万行代码，新同事根本没法读完。这时候就需要向量索引帮他做语义层面的导航。

---

不过双轨制有一个前提条件，没这个前提，双轨制就是无源之水。

> **一切上下文资产，必须以当前代码为事实基准。**

这句话听起来像废话，但实际操作起来 99% 的团队都做错了。

错的方式是这样的：spec 写好了，归档到 Confluence。代码迭代了 100 次，spec 还是当初那一版。你以为你在按 spec 工作，其实 spec 早就跟代码对不上号了。新同事来了拿着 spec 干活，撞到一堆"为什么代码跟文档不一样"的疑问。Senior 说，啊那个 spec 过时了，你直接看代码吧。

这一刻，spec 就死了。它从"上下文资产"降级为"考古文物"。

正确的方式是 ——

代码是事实，spec/AGENTS.md/skill 是注解。注解必须随时跟事实拉齐，否则注解的价值是负的。之所以是负的，因为它会主动误导读到它的人。

具体落地有几个原则：

代码改动是触发文档更新的源头，不是反过来。任何一段文档，如果跟代码冲突了，默认代码对、文档错。

PR 阻断 check 应该是"代码改了、文档没改"，不是"文档改了、代码没跟上"。因为现实工程里，代码先行是常态，文档先行是奢侈品。

向量索引完全是代码自己的影子，它天然跟代码同步，所以是事实的另一种呈现形式。

AGENTS.md / spec 文档必须定期"对账"。最低限度每个季度跑一次自动 diff，用 LLM 把代码当前行为和文档描述做对比，列出所有不一致的地方。

承认这一点之后，双轨制才真正成立 —— 它不是"代码和文档地位平等"，而是"代码是基准，文档是为了让 AI 和新人更快理解代码而存在的辅助层"。辅助层失效了不可怕，只要基准在，辅助层可以随时重建。基准错了才可怕。

这个判断决定了自动维护机制该怎么设计。

## 五、上下文自动维护的四种工程化路径

到这里很多读者应该已经在想一个非常实际的问题：AGENTS.md 这种东西，谁来维护？

如果靠人来手动同步代码变更，三个月之后它一定会过时。Spec drift（规约漂移）是行业公认的核心痛点。代码成了事实标准，因为只有它不会过时。

这件事的工程化解法目前有四种，可以按团队的成熟度逐级演进：

第一种：Git Hook 触发

最朴素的方案。在 pre-commit 或 post-commit 里加一个钩子，代码变更时自动调 LLM 提取摘要，更新 AGENTS.md 的对应段落。简单可靠，但比较粗暴，容易把所有改动都塞进去导致 AGENTS.md 膨胀。

第二种：CI/CD 集成 + Spec Drift Detection

在 PR 流水线里加一个检测步骤。用 LLM 把代码变更和现有 spec 做对比，标记不一致的地方，作为 PR check 阻断合并。Augment Code 和 OpenAI Codex 内部都在用这个模式。比 Git Hook 精细，但需要 CI 改造。

第三种：Agent Hook 触发

这是 Claude Code 推荐的"AI 自我维护"模式。利用 PostToolUse hook，每次 AI 写完代码后自动触发另一次 LLM 调用，让 AI 自己检查并更新 CLAUDE.md / Skills。2026 年 Anthropic 还推出了 HTTP hooks 和 Prompt hooks，让 hook 可以调远程服务、可以让模型评估语义条件。

第四种：增量向量索引

这是国内大厂的方案。文件保存就触发增量索引，IDE 后台静默运行，对开发者完全无感。代价是这个索引不可见、不可 review、不可版本化，是黑盒。

实际落地的时候，建议显式那一轨用前三种组合（Git Hook 处理日常、CI 处理 PR、Agent Hook 处理 AI 自身的写入），向量那一轨用第四种（IDE 层自动）。两条轨道并行，谁也不替代谁。

## 六、动手之前：仓库需要长什么样

方法论清楚之后，真正动手之前还有一步。这套体系跑起来，仓库本身需要做一些改造。没有这些基础设施，上面所有的方法论都是悬空的。

按照优先级，至少要准备好这五件事。

1\. AGENTS.md 的根文件 + 子目录覆盖结构

主仓库根目录必须有一个AGENTS.md，写五件最关键的事：项目是什么、怎么 build、怎么测试、核心目录在哪、有哪些已知陷阱。这是新人和 AI 的"入口文件"。

如果项目大，单文件撑不住，按子目录拆 ——frontend/AGENTS.md写前端约定，backend/AGENTS.md写后端约定。AI 工具会自动按路径就近原则加载。

要点：这个文件的写作风格用陈述句，不要用命令式。"这个 repo 用 bun test"比"请使用 bun 来运行测试"更准确、更短、AI 也更容易遵守。

2\. 一个独立的 ai-context 仓库（或同仓库的.arch/目录）

Skills、扫描脚本、定时任务这些"AI 配套设施"，不要塞在代码主仓里。要么单独建一个-arch仓库，要么在主仓里建一个arch/目录专门管这些。

为什么要分开？因为它们的演化节奏跟代码不一样。代码改一行可能不用动 AI 上下文，AI 上下文调一次可能影响所有人。它们的 review 流程、版本节奏、code owner 都应该是独立的。

3\. 一套 Hook / CI 强制规则

至少要有这三条：

PreToolUse hook：AI 在执行任何写入操作（写文件、跑命令）之前触发的钩子。最常见的用途是 lint、format、危险命令拦截（比如rm -rf、生产环境 deploy）。

PostToolUse hook：AI 写完代码之后触发，可以自动跑测试、自动检查 AGENTS.md 是否需要更新。

PR check：spec drift detection：每个 PR 跑一次 LLM 对比，检查代码变更和 AGENTS.md 描述是否仍然一致。不一致的标红、阻断合并。

这三条是"上下文工程化"的最小可用集。少一条都会有缺口。

4\. 代码扫描器（结构提取 + 业务标注 + 技术债识别）

针对老项目，需要一个能扫描整个 codebase 的工具链。Thoughtworks 的 CodeConcise 是开源参考实现，做法是：用 AST 解析提取代码结构、用 LLM 给函数和模块生成业务摘要、把结果存进向量+图数据库。

如果不想自己搭，也可以用现成方案：

轻量级：用 Claude Code + 一个 skill 让 AI 自己扫，结果写入 AGENTS.md

中等：可以尝试这篇文章推荐的几个框架 [CodeGraph vs Graphify vs code-review-graph vs GitNexus：4 个“代码知识图谱”工具怎么选？](https://mp.weixin.qq.com/s?__biz=MzkwNDUxOTU2OQ==&mid=2247488438&idx=1&sn=85f06bc28c0970a9b998df1370172afa&scene=21#wechat_redirect)

重度定制：自建向量库 + 图数据库 + 自己的 RAG 层

选哪种取决于团队规模和定制需求。但最低限度，你需要一个能"读完整个项目并给出结构化摘要"的工具。

5\. 一个跟代码同生命周期的"对账机制"

最容易被忽略但最重要的一条。"代码是事实、文档是注解"这条原则，靠对账机制才能真正落地。

最简单的实现：写一个定时任务，每周一早上跑一次。让 LLM 对比 AGENTS.md 描述和当前代码行为，列出所有不一致的地方，发到团队群。让 reviewer 决定 —— 是改代码、还是改文档、还是这条不一致是合理的可以忽略。

这个机制比扫描器更重要。因为扫描器只解决"建立"问题，对账机制解决"持续保鲜"问题。没有对账，AGENTS.md 用不了三个月就会从资产变成负担。

---

这五件基础设施搭起来，方法论才有立足点。

整套基础设施从零搭起来，一个中等规模团队大概需要 2-3 周。前两周主要是搭工具链，第三周是写第一版 AGENTS.md 和扫描存量。投入听起来不少，但跟一次线上故障的损失比，便宜得多。

## 七、上下文工程的完整闭环：入库 → 维护 → 接入

基础设施就位之后，整个上下文工程体系是一个三阶段的闭环：

阶段一：存量入库

针对老项目，第一次建立 AGENTS.md / Skills 系统。这是最难的一步，因为存量知识全在老员工脑子里和老代码注释的字里行间。

具体可以拆成四步走：

代码结构提取（自动）。AST 解析 + 依赖图构建。Thoughtworks 的 CodeConcise 工具就是这个思路，从遗留代码库提取代码结构和依赖，在向量和图数据库中构建知识图谱。

业务背景标注（LLM + 人工 review）。LLM 读代码、注释、历史 commit message，生成业务功能摘要，人工 review 确认入库。

技术债/上下文债识别（LLM 扫描 + 人工分类）。找出"无人认领"、"测试缺失"、"过时依赖"、“无法解释的业务逻辑”的区域，标注严重程度。

入库 + 版本化。写入 AGENTS.md /上下文资产路径或仓库/ Skills，进入 Git，跟代码同生命周期。

这一步最大的瓶颈不是技术，是没人愿意花时间做第 2 步和第 3 步的 review 确认。机器扫描可以自动，但"这个判断是不是对的"必须人来拍板。一个 70 万行的项目，扫出来几百条候选条目，谁来做这个 review？这是组织问题，不是技术问题。

我的建议是：把它纳入团队的季度 OKR，每季度啃一个屎山模块，啃完入库。一年下来，最关键的四五个模块就齐了。

阶段二：实时维护

这一阶段就是上一节说的四种自动维护路径。它解决"增量问题"。

这里有一个我自己的强观点。上下文审计这件事，绝对不应该靠人。

很多团队的做法是搞"上下文审计会"，让每个人列出"只有我知道但没写下来的事"。我试过，效率极低，因为人对自己脑子里隐性知识的觉察力是很差的。你知道的事情里有 80% 你自己都不知道你知道。

正确的做法是让机器去发现。让钩子或者定时任务定期扫描代码，找出最近三个月被修改但 AGENTS.md 没同步的模块、找出 if-else 分支密度异常高但没有注释的代码段、找出测试覆盖率突然下降的区域。机器把这些可疑点扫出来摆到桌面上，人的决策只在最后一公里 —— 评估这个识别出来的不良设计/技术债到底要不要处理。

把人的判断力用在"决策"上，把人的体力用在"输入"上，是完全不同的两种工作模式。前者可持续，后者注定崩盘。

阶段三：新人接入

闭环的最后一段，也是开头我们团队故障的根本场景。

传统的新人 onboarding 方式有三件法宝。看代码、问 senior、读 wiki。三件全是不可靠的。代码看不完，senior 没空，wiki 早过时。我团队那个新同事的故障，就是这三个机制同时失灵的结果。

新的接入流程可以这样设计：

地图阅读期（第 1-2 天）。新人读 AGENTS.md。这一步不应该超过半天，因为 AGENTS.md 应该是"地形图"而不是"百科全书"。

技能演练期（第 3-7 天）。跑过几个核心 Skills（debug 流程、code review 清单、测试规范），用 AI 配合完成几个 well-scoped 任务。这阶段的目标是熟悉工具链。

Shadow 实战期（第 2-3 周）。接一个真实的小 bug，AI 全程协作。关键规则：senior 不直接讲，让新人通过 AI + 文档自己摸出来。遇到 AI 也答不上的盲点，全部记下来。

反向贡献期（第 4 周）。新人提交一份"我入职第一个月遇到的所有'AI 没回答好'的问题"清单。这份清单直接变成 AGENTS.md / Skills 下一轮迭代的输入。

阶段三和阶段一在这里闭环。新人的盲点就是存量入库的输入。每来一个新人，相当于做了一次"上下文压力测试"。他卡住的地方，就是上下文资产的漏洞。把这些漏洞补上，下一个新人就少卡一次。

这是阶段一最有效的迭代方式。比一切人工审计都强。

阶段四：日常开发的工作流

入职流程跑完，新人进入了日常开发的常态期。这一阶段也需要一套标准化流程，否则前面的所有投入会逐渐稀释。

一个理想的日常开发节奏长这样：

接到一个任务之后：

先让 AI 读 AGENTS.md + 现有工程文档基线。不要直接动手写代码。AI 读完会告诉你"这个改动会涉及哪些模块、哪些已知约束、哪些历史陷阱"。如果能够对接现有codebase系统或开源codebase框架，对现状的全盘了解能够更深入一层

让 AI 做一次"上下文检索"。用向量索引找到所有相关代码片段，结合 AGENTS.md 的设计意图，输出一份"修改计划"。这份计划是给你看的，不是直接执行。

你 review 计划。这一步是工作流里最关键的一步。AI 给的计划可能在某个地方理解错了，可能漏掉了某个边界。你的判断力用在这里，而不是用在"读代码"上。

AI 执行，你监督。在 PreToolUse hook 的保护下，AI 写代码、跑测试、提交。你看的是 diff 和测试结果。

PostToolUse 自动同步上下文。AI 写完代码后，钩子自动检查 AGENTS.md 是否需要更新。如果需要，AI 自己生成更新草稿，你确认后入库。

遇到 bug 的时候：

不要让 AI 直接修。先让 AI 走"根因分析"路径 —— 这是 debugging skill 应该强制的事情。AI 必须先回答"为什么会发生"再回答"怎么改"。

如果 AI 答不上，说明上下文有缺口。这就是新一条 AGENTS.md 入库的素材。

修复之后，验证 fix 是否对应到了 AGENTS.md 里的某条约束。如果对应了，但代码里没体现，说明之前那条约束没被 hook / CI 强制 —— 这是一次升级强制规则的机会。

遇到老模块的时候：

优先用 AI 做"考古"。让 AI 读这段代码 + 历史 commit + 相关 issue / PR 评论，输出一份"这段代码的设计意图猜测"。

跟现有的 AGENTS.md 对账。如果 AGENTS.md 没提，这就是一次必须做的入库决策—— 这段代码的设计意图，到底要不要写进文档？

如果决定要写，AI 生成草稿，你 review 入库。如果决定不写，为什么不写也要简单记一下，避免下次重复评估。

这一套流程的核心不是"用 AI 写代码"，而是"让每一次开发任务都顺手沉淀上下文资产"。开发本身的效率提升只是表象，真正的复利在于：你每完成一个任务，上下文资产就增厚一层。三个月之后，你团队的 AGENTS.md / Skills 会比同行厚两个量级，AI 工具在你这里能发挥的功力也会比同行高一个量级。

这才是上下文工程真正的飞轮。

## 八、Takeoff：可以参考的五件事

第一件：今天就在你主项目根目录建一个 AGENTS.md。

不用追求完美。先写五节最关键的，构建命令、测试命令、部署流程、代码规范、已知陷阱。每节三五条。总长度控制在一屏以内。

这件事看起来不起眼，但只要存在，它就会开始被维护。完美的 AGENTS.md 是写不出来的，但活的 AGENTS.md 是养出来的。第一版只要存在，后面每次 PR 就会有人补一行、改一行。三个月后回头看，它会比你今天能想到的版本好得多。

第二件：把"上下文审计"做成定时钩子，不要做成人工流程。

这件事的关键是把人从"找问题"里解放出来，放到"判断要不要修"上。配一个每周跑一次的脚本，自动扫描 —— 最近被频繁修改但 AGENTS.md 没动的文件、注释覆盖率异常低的模块、if-else 分支密度过高的代码段。把扫描结果发到团队群，只让人做"要不要修"的决策，不让人做"在哪里找问题"的体力活。

这一条之所以重要，是因为人对自己知识盲区的觉察力极差。机器扫描出来的"可疑点"，是人靠主观回忆永远列不全的。

第三件：下次 PR 开始，把 AGENTS.md 是否更新作为强制 check。

如果一个 PR 改了核心模块的逻辑但没动 AGENTS.md，CI 直接阻断合并。这条规则一开始会被骂，但坚持两周后会变成习惯。

这一条之所以重要，是它把上下文维护从"觉悟"变成"流程"的关键一步。觉悟靠不住，流程才靠得住。

第四件：下个新人入职时，跑一次"上下文压力测试"。

第一周不安排导师讲解。让他用 AI + 现有 AGENTS.md 自己摸到第 5 天。然后让他提交一份卡壳点清单。这份清单就是你团队上下文资产的体检报告。

这一条之所以重要，是因为新人是你团队唯一没有被 stockholm syndrome 影响的人。老员工早就把所有的"反直觉"都内化了，他们觉得理所当然的事情，对新人来说就是地雷。压力测试是把地雷暴露出来最快的方式。

第五件：把"季度啃一座屎山"纳入团队 OKR。

每个季度选一个最痛的老模块，走完"扫描 → 标注 → 入库"三步。一年下来四五个最关键的模块就齐了。

这一条之所以重要，是因为屎山的处理逻辑跟减肥一样，关键不是强度，是持续性。同样的，你今年审视不完所有屎山，但你可以每季度理清一座。

## 收尾

回到开头那个被删除的运维资源。

不是新同事的错。他做的判断在他拥有的信息内是合理的。

也不是三年前那个加 if-else 同事的错。他在那个时间点解决了一个紧急的容灾问题。

真正缺失的，是那个 if-else 和"为什么需要它"之间的桥。桥建在那个离职同事的脑子里，没铺到代码外面去。等他离职，桥跟他一起走了。

新同事看到了 if-else，看不到桥。他就自己搭了一座新桥。新桥搭错了。

---

最深的技术债，不是代码的债，是上下文的债。

代码债可以重构慢慢还。上下文债只能从今天开始，一行 commit、一次 PR、一个新人，把它从人脑里搬到仓库里。

这件事现在做，一年后团队比同行轻松一个数量级。
