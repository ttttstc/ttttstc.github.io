## 一、代码作为资产为什么失效

过去十几年,软件公司默认核心资产是代码。

谁拥有代码,谁拥有产品。这个判断在Agent编程之后失效。

代码本身有三个负债属性。Agent编程把这三条全部放大。

```nix
代码会腐烂          ← 框架升级 / 依赖变化 / 环境变化 / 业务变化
代码会隐藏意图      ← 写得清楚"现在怎么做", 不一定写"为什么这么做"
代码会制造审查负担  ← 人脑审查产能不能等比例扩展, Agent生成速度可以
```

第三条最致命,因为它放大成一个结构性非对称。

```makefile
Agent生成: 几分钟几千行, 低成本, 可并行, 可无限复制
人类审查: 几小时几天,   高责任, 强上下文, 重认知负担
```

![图片](https://mmbiz.qpic.cn/mmbiz_png/S8CROAYnibpFMuaHSb92uopHeyvEge0oGUW7OIiaIEPSgPHsoEhuVUlJPNibkZG24c3yXgf1z44Va5ibYzofXNaEicWg7bq6TQJgxkLzvxBfMBzQ/640?wx_fmt=png&from=appmsg&watermark=1&tp=webp&wxfrom=5&wx_lazy=1#imgIndex=0) 更麻烦的是,Agent生成的代码大部分都「几乎对」。

**「几乎对」的危险，不在于它不对，而在于局部合理的变更让审查者丧失警惕。**

- 新增一个依赖,打破生产环境的部署约束
- 复用一个工具函数,破坏了它在另一处的隐性语义承诺
- 为过测试写出脆弱的分支兜底
- 删掉一个「看起来无用」的兼容字段,撞上老版本客户端的崩溃

Agent带来的新型技术债,不只是更多代码,是更多有测试、有类型、有错误处理、看起来很工程化,却没对齐业务语义、架构边界和长期演进方向的代码。

这不是「代码不重要了」。

**这是「代码不再适合做资产」。**

代码会被更新的代码替换、被更强的模型重写、被新的依赖淘汰。

那什么不会被替换?

下面谈谈我对AI工程资产的理解。

## 二、对知识分层的理解

我个人把仓库知识资产知识分为三类

**工程基础知识**

包括 设计语言、编码规范、技术架构及选型、API 、数据模型、验收标准、可信要求 等。这类知识与代码现状强绑定，一旦不一致就会影响交付质量，必须进入工程基线 作为事实源。每次变化，都能和代码在同一条变更链路里被追踪。

**工程交付知识**

PRD 、ADR、方案讨论、评审意见等。先随变更放在 `change-requests/CR-*` 下，等评审通过、代码合并、测试完成后，再把稳定部分沉淀到 `specs/` 或 rules `/` 。每次只追加，不修改。

**探索与协作知识**

项目介绍文档、教程文档、新人学习路径等。每次可以由事实源提取自动生成wiki，由 LLM负责检索、摘要和问答。

### wiki文档 vs rules契约？

```
wiki文档    写给人看, 可以过期, 过期了写一句"以代码为准"还能撑半年
rules契约    写给Agent和人共读, 过期立刻产生事故, 因为Agent会照过期版本生成
```

**文档和契约的差别，不在于措辞精不精确，而在于有没有可执行的违反检测。** 没有检测方式，写在 README 里三个月就死。挂上可执行命令、代码改一次跑一次，才是活的约束。

**Wiki 擅长解释，不擅长负责** 。负责这件事，仍然要回到团队自身的代码事实源和契约上来

**知识资产的定位因此要收敛：**

**工程基础知识和交付强相关：spec和rules为主事实源，LLM 辅助阅读检索**

探索和协作类：由事实源生成，wiki作为主力，优化阅读体验

## 三、知识资产清单分类

本文我们重点讨论契约层的知识，我把契约层知识资产清单按职能分 4 大类。每类回答一个不同的问题。

| 类别 | 回答的问题 | 不写的代价 |
| --- | --- | --- |
| 1\. 系统意图层 | 系统为什么存在, 价值优先级是什么 | Agent删兼容字段, 把未知态改失败态 |
| 2\. 规约层 | 团队规范怎么传, Agent怎么干活 | 新人重复踩坑, Agent每次从零摸索 |
| 3\. 边界与协作层 | 模块怎么相处, 接口承诺什么 | Agent跨层调用, 破坏隐性语义 |
| 4\. 风险与历史层 | 哪里是地雷, 为什么有这些地雷 | Agent重蹈覆辙 |

每一类都不是过去意义上的「文档」。

是Agent可读、可被合并请求校验、可被钩子触发的契约层。

### 规约层:代码化的知识

传统团队规范的载体是内部知识库、入职文档、资深工程师的口传心授。

这些载体的共同特征是,**一旦写出来就开始过期,而且没人有动力维护** 。

Agent编程时代有一个新做法。

```
传统团队知识传承:
  口传 → 入职文档 → 内部知识库 → 过期 → 资深口头补充 → 又过期

代码化的知识 (Knowledge as Code):
  规范编码为技能 → 跟代码同仓 → 合并请求校验 → 修改触发更新 →
    新人入职时Agent自动加载 → 跨人传承
```

**代码化的知识不是把 wiki 搬进仓库，是给每条知识挂上可执行的校验命令。**

一是团队规范(编码风格、设计原则、命名约定、错误处理模式)。

二是Agent操作手册(读哪些文件、不确定时停在哪、灰度策略、回滚预案)。

过去这两件事的载体不一样,前者是入职 wiki,后者是运维手册。Agent编程时代,两者都该走「代码化的知识」这条路,合成一类。

**这是Agent编程时代独有的资产形态。**

### 风险与历史层包含两类新东西

除了行业熟悉的架构决策记录、测试缺口表、风险登记,还要加两类新东西。

```
反常点地雷地图
  老代码里"看起来不对劲但稳定运行很久"的地方, 逐条标出来
  哪怕没人解答, 标出来就是高密度风险预警

编码事实约定
  不是团队想要的规范, 是代码里事实上的多数派一致
  比如 95% 接口返回 Result 包装, 3 处例外
  让"约定"也能Agent起草 + 人确认, 不再等人从零写
```

这两类在传统文档体系里没有位置,但在Agent编程时代是高价值资产。

**没有它们,新人和Agent都会反复踩同一颗雷。**

## 四、从三个源头挖掘/抢救老代码库上下文债

新项目从零建这套体系,难度不大。麻烦的是老代码库。先立一个硬约束：所有事实层必须完全来源于代码,每一行都能在代码里找到证据。这是代码资产的底座——用成熟扫描框架跑出基线,确保 **事实层能反映当前代码真实现状**,也是往上追求高阶关键资产的前提。

我们这里讨论的关键资产，是把这层再往前推一层。

能被Agent扫描识别的,是可重入、可快速构建的确定性资产。 **而老代码库真正的关键资产,绝大多数不在文档里,在老员工脑子里。**

针对老代码库的这个痛点，我的想法是通过以下三板斧进行深度挖掘：

```nix
机器考古    从代码行为反推隐性约束
            扫依赖关系 / 字段修改链 / 接口响应模式
            输出: 隐性依赖规则 / 数据不变量 / 接口语义承诺

反常侦查    标出"看起来不对劲但稳定运行很久"的地方
            7 类反常: 吞异常 / 反模式 / 命名不一致 / 老 TODO 等
            输出: 可疑度 × 影响面 评分的反常点清单

人脑访谈    抢救老员工脑子里的"为什么"
            带具体反常点 grill, 不开"上下文审计会"
            输出: 来源 = interview 的提案条目 + 人证留底
```

机器考古能拿到「是什么」,拿不到「为什么」。

这个差别在重构决策上差着一个量级:知道「是什么」只能照旧保留行为,知道「为什么」才能判断什么场景下可以换种实现。

**抢救「为什么」是工程问题,不是组织问题。**

工程问题用工程方法解。

不要走「上下文审计会」的老路。

**这种会开不下去，原因不在于人不愿意说，而在于人察觉不到自己知道什么——你知道的事情里有 80%，你自己都不知道你知道。**

正确的做法,**机器扫,反常侦查排序,人脑访谈定夺** 。

把人的判断力用在 **「决策」** 上,把人的体力用在 **「输入」** 上。

## 五、Agent写的规格,默认是新一类负债

前面三个阶段产出来的,大量是Agent起草的内容。

机器考古的约束、反常侦查的清单、风格统计的事实约定,全是Agent推断。访谈虽然有人证,但记录员是Agent。

Agent写的东西看起来很像规格,字段齐、措辞合规、引用都有。

但本身需要人确认才能算数。

如果没有产权规则,Agent起草的内容直接被当成已确认推进项目,五类典型失败会接连发生。

```
失败 1   Agent反复推同一条误判      ← 没有"驳回"状态保留误判记录
失败 2   Agent覆盖人手改过的版本    ← 没有只追加保护机制
失败 3   Agent起草直接当作硬约束    ← 没有来源区分和状态机
失败 4   约束没检测方式只是口号    ← 没有违反检测字段
失败 5   矛盾点被强压成"低置信度"  ← 没有"有冲突"等级
```

五条失败合在一起,**让"规格资产"反过来变成"规格泥浆"** 。

**规格的关键不在于内容本身，而在于有没有产权规则。没产权的规格，只是另一类负债。**

## 六、五条产权规则

每条规格资产必须刻五条规则。

### 6.1 三态证据等级 + 一个「有冲突」特例

```
已确认 (confirmed)   代码 + 测试 + 文档共同支持, 或人证确认
已观察 (observed)    代码行为或日志能稳定观察到
待定 (uncertain)     无法直接确认, 需要人类判断
有冲突 (conflicted)  多来源之间矛盾, 作为特例独立标
```

为什么必须有「有冲突」?

老代码库审计里,矛盾点是最该问人的信号。

代码这么写、测试那么验、文档又是另一套。

这种地方最容易出事。

**矛盾点不是低置信度,是高优先级。**

### 6.2 三源标注

```
ai-mined    Agent从代码反推, 默认不可信
interview   访谈记录, 带受访人, 权重高于 ai-mined 但需一人复核
human       人工编辑, 默认权威
```

不标来源,Agent错判和人手写规则混在一起。

半年后无法判断哪条该信。

**一份没有来源的规格清单,跟一份没有 git 历史的代码库一样,都是历史断点。**

### 6.3 状态机

```nginx
proposed   Agent起草初稿, 软提示
confirmed  人评审升级为硬约束
rejected   误判, 但保留记录不删
adjusted   人改过措辞或范围后确认
```

「驳回」状态必须保留。

否则Agent下次会重复考古同一误判,陷入死循环。

只有「已确认」是硬约束。

「提案」是软提示,触碰时提醒但不阻塞。

**只有已确认才进硬约束,这条不可妥协。**

### 6.4 Agent起草、人确认产权规则要刻在 schema 里

第四条是核心。

来源是 ai-mined 的条目,默认不能直接升「已确认」。

这条不是写在文档里说说,是写进 schema 的硬规则。schema 验证不过,写盘工具就拒绝写。

只有人手动改来源为 human 或 interview,并且填确认人和确认时间,才能升「已确认」。

为什么必须刻 schema?

**产权规则不能靠流程约束来守。流程靠自觉，schema 靠拒绝。**

**schema 层的硬约束,是产权规则唯一靠谱的工程落点。**

### 6.5 只追加 + 违反检测

第五条管两件事。

只追加历史。

```
架构决策记录提交后不修改, 替代关系走索引
变更请求评审段只追加
状态历史只追加
人确认的条目永不被Agent覆盖
```

违反检测。

```
每条已确认约束挂一个可执行命令
代码改动一次跑一次, 违反立刻发现
```

举几个真实的违反检测命令:

```
"billing-core 不依赖 payment-adapter"
  → depcruise --config dep.config.js services/billing-core

"invoice 进入 issued 状态后金额不可变"
  → pnpm test contract:invoice

"所有公开接口必须返回 Result 包装"
  → eslint --rule require-result-wrap src/api
```

那些「模块之间应该低耦合」「应该做好错误处理」「应该保持向后兼容」的话,挂在 README 里没人能跑、没人能查,三个月后就死。挂上可执行检测命令,才是活的约束。

## 七、我们的代码化的知识建模

把上面五条产权规则套在第三类资产(规约与协作层)上,落到工程,就是 understand-arch 的具体建模。

载体是项目仓库里一个叫 `rules/` 的目录,两层结构。

```
.understand-arch/{project}/rules/
├── 规范层 (人工权威, Agent只读)
│   ├── system-charter.md         系统使命 + 非目标 + 价值优先级
│   ├── banned-patterns.md       禁用模式
│   ├── compliance.md            合规红线
│   ├── naming.md                命名约定
│   ├── network-boundaries.md    网络边界
│   └── dependencies.md          依赖选型
│
└── constraints/ (约束层, Agent考古 + 人访谈, 人确认)
    ├── domain-invariants.md      领域不变量
    ├── dependency-rules.md       依赖方向规则
    ├── api-contracts.md          接口语义承诺
    ├── risk-register.md          高风险区 + 高风险变更规则
    ├── test-coverage-gaps.md     测试覆盖缺口
    ├── suspicious-findings.md    反常点地雷地图
    ├── coding-conventions.md     编码事实约定
    └── interview/                访谈记录留底
        └── interview-{date}-{受访人}.md
```

两层本质不同。

规范层是「人 → 系统」,团队主动定的规矩,永久权威,Agent只读不写。

约束层是「系统 → 人」,从系统反推出来「实际已经怎样、且不能乱动」的护栏,Agent起草,人确认才作数。

**规范层是人写给系统的,约束层是系统通过Agent告诉人的。**

每条约束(无论哪一层)都按统一结构落地。

```
### {约束标题}

- 约束:{不能做什么 / 必须保持什么}
- 依据:{代码 file:line / 架构决策记录编号 / 访谈记录}
- 证据等级:已确认 | 已观察 | 待定 | 有冲突
- 违反检测:{可执行命令}
- 状态:proposed | confirmed | rejected | adjusted
- 来源:ai-mined | interview | human
- 备注:{受访人 + 日期 / 关联反常点编号 / 关联架构决策记录}
```

这个 7 字段结构,**把第六章的五条产权规则全部直接落在 markdown 字段里** 。

约束怎么从无到有?

`arch-constraint-miner` 这个 subagent 一次产三份产物,全部默认 `source: ai-mined` + `status: proposed` 。

```
arch-constraint-miner 一次产三份:
  ─ 隐性约束考古
  │   产 dependency-rules.md / domain-invariants.md / api-contracts.md /
  │   system-charter.md 的候选条目
  ─ 反常点侦查
  │   产 suspicious-findings.md, 7 类反常点 + 可疑度 × 影响面评分
  └ 编码事实约定统计
      产 coding-conventions.md, 95% 多数派一致约定 + 例外列表
```

三份产物本质同源,都是「从图谱里找出值得注意的点」,在一个 subagent 里聚合产出。

然后是人的环节。

```
人评审约束层 → 升级路径:
  proposed (Agent初稿)
     ↓ 人点头
  confirmed (硬约束, 违反 = 阻塞合并)

或者:
  proposed → rejected   (误判, 但记录保留, Agent下次跳过)
  proposed → adjusted   (人改过措辞 / 范围后确认)
```

编码事实约定还有一条特殊升级路径。 `coding-conventions.md` 里的条目,人确认后可以 **升级进规范层** ，这条让规范层也能被Agent起草初稿,不再等人从零写。

跟传统团队知识传承的对照很清楚。

```
传统:  知识 → wiki → 新人靠记忆 → 过期 → 资深口头补
现在:  知识 → rules/ 约束条目 → 7 字段 schema 校验 →
        arch-constraint-miner 起草 → 人 confirm 升级 →
        arch-review 强制对照 → arch-audit 检测漂移
```

载体从「自由文档」变成「带 schema 的结构化条目」

生命周期从「跟项目分离」变成「跟代码同合并请求」

更新动力从「靠资深勤奋」变成「Agent起草 + 人评审 + 钩子检测」。

**代码化的知识不是「把 wiki 写得更全」,是把每条知识变成一个带证据、带来源、带状态、带检测命令的工程对象。**

## 八、控制点的迁移

当代码不再稀缺,工程师应该站在哪里?

工程师真正的新工作,是为Agent设计这套生产 + 治理的规格约束体系。

四件事。

```nix
定义资产清单     4 类资产各自该长什么样
设计生产管线     机器考古 / 反常侦查 / 人脑访谈的工艺
设计产权规则     三态 / 三源 / 状态机 / 产权 / 只追加 / 违反检测
做最终确认       终审权
```

合起来是一个新的工程师画像。

过去的架构师画图给人看,新角色定规则给Agent看。

过去的运维写流水线给代码跑,新角色写 schema 给Agent跑。

过去的资深工程师在代码评审里教新人,新角色在验收关卡里设计「让Agent没办法假装完成」的关口。

这不是头衔的迁移,是控制点的迁移。

**代码生产被外包给Agent,规格生产和终审权被人收回。**

## 收束

代码生产变得便宜,但「什么不能被乱改」变得珍贵。

**AI 工程的高质量资产,不是某一版代码,是一套能被Agent读、被人审、可生产、可治理的规格约束体系。**

代码可以被一代一代模型重写。这套规格约束体系不能。

模型决定Agent的上限。规格约束决定系统能不能跨模型活下去。

下一篇会用 understand-arch 这个工具,把五条产权规则和「代码化的知识」建模的完整工程实现拆开讲。是这套思想跑得通的证据。
