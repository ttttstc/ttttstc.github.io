# vibeflow-design — 技术设计

## 概述

`vibeflow-design` 用于编写技术设计文档，包含 UCD 内联和三视角评审。

---

## 目标

- 技术方案详述
- 接入点和 API 设计
- 数据模型
- 三视角评审
- 用户逐节审批

---

## 设计流程

```
0. [可选] 问题探索 ── vibeflow-brainstorming
           │
           ▼
1. 读取 SRS + UCD ── 需求和用户体验设计
           │
           ▼
2. 探索上下文 ── 了解技术环境、依赖、约束
           │
           ▼
3. 提出方案 ── 多个方案对比
           │
           ▼
4. 用户逐节审批 ── 获得用户签字确认
           │
           ▼
5. AI 深度评审 ── 工程视角 + 设计视角
           │
           ▼
6. 范围决策 ── Expand / Hold / Reduce
           │
           ▼
7. 编写设计文档 ── 最终技术方案
           │
           ▼
8. 过渡到初始化 ── Build 阶段准备
```

---

## 三视角评审

### CEO 视角（Plan 阶段）

关注：**价值** — 这个设计是否服务于业务目标？

### 工程视角（Design 阶段末尾）

调用 `vibeflow-plan-eng-review`，关注：
- 架构是否合理？
- 技术选型是否恰当？
- 代码质量是否可控？
- 是否有安全隐患？

### 设计视角（Design 阶段末尾）

调用 `vibeflow-plan-design-review`，关注：
- 用户是否能流畅完成目标？
- 信息架构是否清晰？
- 交互是否直观？

## 范围决策

| 决策 | 含义 |
|------|------|
| **Expand** | 范围扩大，增加功能 |
| **Hold** | 保持当前范围 |
| **Reduce** | 范围收缩，削减功能 |

---

## 产出物

`docs/changes/<change-id>/design.md`，包含：
- 设计决策和 rationale
- 技术方案详述
- 接入点和 API 设计
- 数据模型
- UCD 内联（如有 UI）

`docs/changes/<change-id>/design-review.md` — 三视角评审结论

---

## 注意事项

- 好的设计是优雅的解决方案，不是复杂的堆砌
- 记录每个决策的"为什么"
- 预留扩展性，但不要为"可能永远不来"的需求提前付出成本
