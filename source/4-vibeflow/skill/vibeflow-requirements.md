# vibeflow-requirements — 需求规格

## 概述

`vibeflow-requirements` 用于编写需求规格说明书（SRS），遵循 ISO/IEC/IEEE 29148 标准。

---

## 目标

- 编写清晰、可验证的需求规格
- 逐条与用户确认
- 每条需求可测试

---

## SRS 模板结构

```markdown
# 需求规格说明书

## 1. 概述
### 1.1 目标
### 1.2 范围
### 1.3 定义与缩略语

## 2. 功能需求
### 2.1 用户故事
### 2.2 功能详细描述

## 3. 非功能需求
### 3.1 性能需求
### 3.2 安全需求
### 3.3 可用性需求
### 3.4 可维护性需求

## 4. 验收标准
### 4.1 验收条件
### 4.2 验收测试用例
```

---

## 需求编写原则

### 每条需求可测试

| 不好的需求 | 好的需求 |
|-----------|---------|
| "系统要快" | "API 响应时间 P95 < 200ms" |
| "要支持并发" | "同时支持 1000 并发用户" |
| "界面要友好" | "新用户完成首次操作 < 3 分钟" |

### 用户故事格式

```
作为 [角色]
我希望 [功能]
以便 [价值]
```

### 验收条件

```markdown
## 需求：用户登录

### 验收条件
1. 用户输入正确用户名和密码 → 登录成功
2. 用户输入错误密码 → 显示"密码错误"
3. 用户输入不存在用户名 → 显示"用户不存在"
4. 连续 5 次登录失败 → 锁定账户 15 分钟
```

---

## MoSCoW 优先级

| 优先级 | 含义 |
|--------|------|
| **Must have** | 必须有，否则项目失败 |
| **Should have** | 应该有，但不是致命的 |
| **Could have** | 可以有，但不影响核心 |
| **Won't have** | 这版不做 |

## 产出物

`docs/changes/<change-id>/requirements.md`

---

## 注意事项

- 需求是开发的契约，每一条都值得认真对待
- 不要在需求阶段写实现方案
- 不要用模糊词汇（"等"、"或"）
- 不要镀金（做超出需求范围的功能）
