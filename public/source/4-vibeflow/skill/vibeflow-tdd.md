# vibeflow-tdd — 测试驱动开发

## 概述

`vibeflow-tdd` 是 Build 阶段的 Red-Green-Refactor 步骤。强制测试先行开发。

---

## 铁律

```
没有失败测试就没有实现代码
```

先写了代码再写测试？删掉。重来。没有例外。

---

## Red-Green-Refactor 循环

```
TDD Red：编写失败测试 → TDD Green：最小实现 → TDD Refactor：清理
```

---

## 步骤 1：TDD Red — 编写失败测试

为功能规格中的**所有** verification_steps 编写测试。测试**必须失败**。

### 测试场景规则

| 类别 | 测试什么 | 示例 |
|------|---------|------|
| **正常路径** | 正常操作，有效输入 | 有效登录返回 token |
| **错误处理** | 已知故障，无效输入 | 无效密码返回 401 |
| **边界/极端** | 限制，空值，最大值，零值 | 空字符串；最长密码 |
| **安全** | 注入，授权 | 用户名中的 SQL 注入 |

### 负面测试比例 >= 40%

```
negative_test_count / total_test_count >= 0.40
```

### 断言质量 — 低价值 <= 20%

避免低价值断言：
- `assert x is not None` 不检查内容
- `assert isinstance(x, SomeType)` 不检查行为
- `assert len(x) > 0` 不验证元素

---

## 步骤 2：TDD Green — 最小实现

写**仅够**让测试通过的代码。

- 从测试出发全新实现
- 一次一个测试
- 不过早优化或额外功能

---

## 步骤 3：TDD Refactor

保持测试绿色的同时清理：

- 提取重复
- 改善命名
- 简化

---

## 测试反模式（前 5 名）

1. **测试 mock 行为** — 验证真实代码，不是 mock 配置
2. **测试实现细节** — 测试行为/输出，不是内部结构
3. **不会失败的测试** — 每个断言必须可证伪
4. **刷覆盖率** — 无断言的测试不验证正确性
5. **低价值断言** — 最多 20%
