# Requirements - 需求阶段

## 目标

**编写需求规格说明书（SRS），遵循 ISO/IEC/IEEE 29148 标准。**

Requirements 阶段是 VibeFlow 流程中的核心文档阶段。这里产出的需求规格说明书是后续所有工作的基础——设计、实现、测试，都要对齐这份文档。

---

## 核心理念

> **需求是开发的契约，每一条都值得认真对待。**

如果需求不清楚，后续的设计和开发就会不断返工。

如果需求不可测试，后续的验收就没有标准。

---

## 产出物

### 需求规格说明书（SRS）

产出 `docs/changes/<change-id>/requirements.md`

### SRS 模板结构

```markdown
# 需求规格说明书

## 1. 概述
### 1.1 目标
### 1.2 范围
### 1.3 定义与缩略语

## 2. 功能需求
### 2.1 用户故事
### 2.2 功能详细描述

## 3. 非功能需求
### 3.1 性能需求
### 3.2 安全需求
### 3.3 可用性需求

## 4. 验收标准
### 4.1 验收条件
### 4.2 验收测试用例
```

---

## 需求编写原则

### 每条需求可测试

好的需求应该是**可验证的**：

| 不好的需求 | 好的需求 |
|-----------|---------|
| "系统要快" | "API 响应时间 P95 < 200ms" |
| "要支持并发" | "同时支持 1000 并发用户" |
| "界面要友好" | "新用户完成首次操作 < 3 分钟" |

### 用用户故事描述功能

```
作为 [角色]
我希望 [功能]
以便 [价值]
```

### 验收条件

每条需求应该附带验收条件：

```markdown
## 需求：用户登录

### 验收条件
1. 用户输入正确用户名和密码 → 登录成功
2. 用户输入错误密码 → 显示"密码错误"
3. 用户输入不存在用户名 → 显示"用户不存在"
4. 连续 5 次登录失败 → 锁定账户 15 分钟
```

## 与 Design 阶段的关系

Requirements 阶段和 Design 阶段是**迭代关系**：

```
Requirements → Design → 发现问题 → 回到 Requirements 修订 → Design 更新
```

不要试图在 Requirements 阶段一次性写出完美的需求。

好的需求是在设计和实现过程中不断完善的。

---

## 实践建议

### 需求逐条确认

与用户/利益相关者逐条确认需求，确保理解一致。

### 优先级排序

用 MoSCoW 方法排序需求：

- **Must have**：必须有，否则项目失败
- **Should have**：应该有，但不是致命的
- **Could have**：可以有，但不影响核心
- **Won't have**：这版不做

### 避免的陷阱

- **镀金**：做超出需求范围的功能
- **模糊**：用"等"、"或"等模糊词汇
- **实现细节**：不要在需求阶段写实现方案

---

## 进入下一阶段

当需求规格说明书完成并获得用户确认后，就可以进入 **Design 阶段** 了。

> 记住：Requirements 阶段的价值不在于产出完美无缺的需求文档，而在于建立开发团队和利益相关者之间的共同理解。
