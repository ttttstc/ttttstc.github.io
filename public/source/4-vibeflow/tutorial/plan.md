# Plan - 计划阶段

## 目标

**CEO 视角价值评审，唯一关卡。**

Plan 阶段是整个 VibeFlow 流程中的 **fail-fast 关卡**。如果价值评审失败，项目直接终止，不再继续投入。

---

## 核心理念

> **先问值不值得做，再问怎么做。**

很多项目失败不是因为技术不行，而是因为一开始就问错了问题。

在开始写代码之前，先问自己：**这件事真的值得做吗？**

---

## 价值评审

调用 `vibeflow-plan-value-review` 进行 CEO 视角价值评审。

### 评审维度

| 维度 | 问题 |
|------|------|
| **价值** | 解决了什么问题？创造了什么价值？ |
| **市场规模** | 目标用户是谁？市场有多大？ |
| **竞争壁垒** | 相比现有方案，你的优势是什么？ |
| **执行风险** | 最大的风险是什么？能承受吗？ |
| **时机** | 为什么是现在？早做或晚做有什么影响？ |
| **退出策略** | 如果不 work，下一步是什么？ |

### 评审结果

- **通过**：继续进入 Requirements 阶段
- **失败**：项目终止，记录 lessons learned

---

## 评审模板

### 问题框定

```
我们要解决的问题是：___________
当前用户/客户的现状是：___________
我们预期带来的改变是：___________
```

### 价值论证

```
直接价值：___________
间接价值：___________
战略价值：___________
衡量指标：___________
```

### 风险评估

```
技术风险：___________
商业风险：___________
缓解措施：___________
```

## 为什么是 fail-fast

很多创业公司死于"确认偏误"——因为太喜欢自己的点子，所以一直往里投资源，直到弹尽粮绝才发现不对。

VibeFlow 的 Plan 阶段就是要在 **投入工程资源之前**，先做一个冷静的评估。

如果连自己都说服不了自己这件事值得做，那就不要开始。

---

## 与 Design 阶段的关系

很多团队把"工程视角评审"和"设计视角评审"放在 Plan 阶段。

VibeFlow 的做法是：**把这些评审移到 Design 阶段末尾**。

原因是：Plan 阶段还没有具体的设计文档，没有东西可以评审。

只有到了 Design 阶段，有了具体的技术方案，才能进行有意义的工程和设计评审。

---

## 实践建议

### 写好价值陈述

一个好的价值陈述应该：

1. **具体**：不是"提升效率"，而是"减少 50% 的重复操作"
2. **可衡量**：有明确的指标可以追踪
3. **有边界**：明确目标用户和使用场景

### 避免的陷阱

- **过度乐观**：低估风险，高估收益
- **自嗨**：基于"我觉得"而不是用户调研
- **完美主义**：试图在 Plan 阶段解决所有细节

---

## 进入下一阶段

当价值评审通过后，就可以进入 **Requirements 阶段** 了。

> 记住：Plan 阶段的价值不在于产出完美的商业计划，而在于让你冷静思考这件事到底值不值得做。
