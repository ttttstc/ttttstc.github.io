# Design - 设计阶段

## 目标

**技术设计 + 用户体验设计 + 三视角评审。**

Design 阶段是 VibeFlow 框架中最复杂的阶段。它不仅是写技术文档，还要完成三视角评审，确保设计是合理的、完整的、可执行的。

---

## 核心理念

> **好的设计是优雅的解决方案，不是复杂的堆砌。**

设计阶段的目标不是展示技术能力，而是找到**最简单、最有效的解决方案**。

## 各步骤详解

### 步骤 0：问题探索（可选）

调用 `vibeflow-brainstorming` 进行问题探索。

适用于：
- 复杂问题，需要多角度思考
- 需要创新解决方案
- 团队需要头脑风暴

产出：`docs/plans/*-brainstorming.md`

### 步骤 1：读取 SRS + UCD

SRS = Software Requirements Specification（需求规格说明书）
UCD = Use Case Diagram（用例图，按需生成）

设计驱动从需求文档中提取关键信息，为后续设计提供依据。

### 步骤 2：探索上下文

了解：
- 技术栈和依赖
- 现有代码库结构
- 运维和部署约束
- 安全和合规要求

### 步骤 3：提出方案

提出**至少两个**可行方案，并进行对比：

| 维度 | 方案 A | 方案 B |
|------|--------|--------|
| 复杂度 | | |
| 开发时间 | | |
| 可维护性 | | |
| 扩展性 | | |
| 风险 | | |

### 步骤 4：用户逐节审批

用户对设计的每个部分进行确认，获得签字。

这是**人工参与的最后一个环节**，之后进入自动执行阶段。

### 步骤 5：AI 深度评审

调用两个独立 skill 进行评审：

| Skill | 评审视角 | 关注点 |
|-------|----------|--------|
| `vibeflow-plan-eng-review` | 工程视角 | 架构、代码质量、测试、性能 |
| `vibeflow-plan-design-review` | 设计视角 | 信息架构、交互、用户体验 |

评审结果沉淀到 `docs/changes/<change-id>/design-review.md`。

### 步骤 6：范围决策

根据评审结果，做范围决策：

| 决策 | 含义 |
|------|------|
| **Expand** | 范围扩大，增加功能 |
| **Hold** | 保持当前范围 |
| **Reduce** | 范围收缩，削减功能 |

### 步骤 7：编写设计文档

产出 `docs/changes/<change-id>/design.md`，包含：
- 设计决策和 rationale
- 技术方案详述
- 接入点和 API 设计
- 数据模型
- 验证方式

## 三视角评审

### CEO 视角（Plan 阶段）

关注：**价值**——这个设计是否服务于业务目标？

### 工程视角（Design 阶段）

关注：**可行性**——架构是否合理？技术选型是否恰当？代码质量是否可控？

### 设计视角（Design 阶段）

关注：**体验**——用户是否能流畅完成目标？信息架构是否清晰？

---

## 实践建议

### 不要过度设计

> 简单是可靠的先决条件。

好的设计应该在满足需求的前提下，尽可能简单。

### 记录决策 Rationale

每个设计决策都要记录**为什么这么选**，而不是只记录**选了什么**。

### 预留扩展性

在设计时考虑未来的扩展需求，但不要为"可能永远不来"的需求提前付出成本。

---

## 进入下一阶段

设计文档完成并获得各方签字后，进入 **Build 阶段**。

> 记住：Design 阶段的价值不在于产出完美的设计文档，而在于建立整个团队对"怎么做"的共同理解。
