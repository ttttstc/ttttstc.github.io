# Think - 思考阶段

## 目标

**定义问题、理解边界、扫描机会、选择工作流模板。**

Think 阶段是整个 VibeFlow 流程的起点。在这个阶段，我们需要明确要解决的问题是什么，边界在哪里，机会在哪里，以及应该选择什么样的工作流模板来应对。

---

## 产出物

### Context 文档

产出 `docs/changes/<change-id>/context.md`，包含：

- **问题描述**：我们要解决什么问题？
- **背景上下文**：为什么现在要做这件事？
- **边界定义**：这个项目的范围是什么？不包括什么？
- **目标与约束**：我们要达成什么目标？有什么硬性约束？
- **机会扫描**：有哪些可能的解决方案？各有什么优劣势？

---

## 可选：Office Hours 头脑风暴

在正式进入 Think 阶段之前，可以先跑一轮 `vibeflow-office-hours`。

这是一个 YC Office Hours 风格的头脑风暴，帮助你验证想法是否值得投入。

### 问自己的六个问题

1. **现实扭曲场**：你在解决什么问题？用户现在是怎么凑合的？
2. **第一性原理**：为什么这是问题？为什么用户需要你？
3. **10 倍改进**：你的方案比现状好多少？够不够值得用户切换？
4. **最窄突破口**：能不能先用最小的方式证明这个想法可行？
5. **观察者视角**：你预期用户会怎么说？能不能找到真实反馈？
6. **退出策略**：如果这个想法不 work，下一步是什么？

## 模板选择

VibeFlow 提供四种工作流模板，选择合适的模板很重要。

### 四种模板

| 模板 | 适用场景 | Think 深度 |
|------|----------|-----------|
| Prototype | 黑客马拉松、POC | quick |
| Web-Standard | Web 应用 | standard |
| API-Standard | API 服务 | standard |
| Enterprise | 企业/合规系统 | deep |

### 如何选择

**选 Prototype 如果**：
- 黑客马拉松或周末项目
- 探索性 POC，需要快速验证想法
- 时间紧迫，需要快速出原型

**选 Web-Standard 如果**：
- 常规 Web 应用开发
- 需要完整的需求→设计→开发流程
- 团队协作项目

**选 API-Standard 如果**：
- 纯后端 API 服务
- 需要详细的接口定义
- 强调稳定性和文档

**选 Enterprise 如果**：
- 企业级应用
- 有合规要求
- 需要完整的审计追踪

## 实践建议

### 写好 Context 的技巧

1. **用一句话说清楚问题**：如果不能用一句话描述问题，说明问题还不够清晰
2. **列出边界**：明确项目不包括什么，有时候比列出包括什么更重要
3. **找真实用户**：如果有真实用户，描述他们的痛点；如果没有，做用户画像

### 避免的陷阱

- **过度分析**：Think 阶段不是要解决所有问题，而是要清晰定义问题
- **完美主义**：先有个初步框架，在后续阶段可以迭代
- **忽略约束**：一定要正视技术、时间、资源约束

---

## 进入下一阶段

当你完成了 Context 文档，明确了问题定义和模板选择后，就可以进入 **Plan 阶段** 了。

> 记住：Think 阶段的价值不在于产出完美的文档，而在于让你清晰自己要解决什么问题。
